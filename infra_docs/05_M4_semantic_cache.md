# M4 — 语义缓存层

> **一句话**：给 LLM 调用加两级缓存——精确缓存（相同请求直接命中）+ 语义缓存（复用已有 embedding 做相似问题命中），降低延迟与成本。
>
> **改造对象**：新增 `app/llm_gateway/cache.py`，接入 M2 的 `LLMGateway`；复用现有 `embedding_service`
> **依赖**：M2（Gateway 是缓存挂载点）、M3（用命中率量化省了多少钱）

---

## 1. 现状缺口

- 每一次问答都真打 LLM，即使用户重复问"我的待办有哪些"
- 已有 `embedding_service`（语义检索用），但没用于缓存
- fast 路径的闲聊、路由判定这类高重复调用完全没缓存

---

## 2. 两级缓存设计

```
请求 → [L1 精确缓存] --命中--> 直接返回
         │ 未命中
         ▼
       [L2 语义缓存] --相似度≥阈值--> 返回缓存答案（标记 cache_hit=semantic）
         │ 未命中
         ▼
       真打 LLM → 写回 L1 + L2
```

### L1 精确缓存
- key = `hash(model + messages + tools)`
- 存储：Redis（有）或进程内 LRU（无 Redis 时兜底）
- 命中条件：完全一致，适合路由判定 / 重复问答
- TTL：可配置（路由类短、事实类长）

### L2 语义缓存
- 对 user query 做 embedding（复用 `embedding_service`）
- 在该 user 的历史 query 向量里找 top-1，cosine ≥ 阈值（如 0.95）判命中
- 关键约束：**按 user_id 隔离**，绝不跨用户命中（隐私 + 正确性）
- 只对"事实性、与时间无关"的查询启用；带时间词（今天/最近）的查询跳过语义缓存（时间敏感，缓存会返回过期答案）

---

## 3. 缓存策略矩阵（哪些该缓存）

| 调用类型 | L1 | L2 | 理由 |
|---------|----|----|------|
| 路由判定（routing） | ✅ | ❌ | 高重复、确定性强 |
| 闲聊 / 通用知识 | ✅ | ✅ | 可安全复用 |
| 对个人记录的问答 | ✅ 短TTL | ⚠️ 谨慎 | 记录会更新，TTL 要短 |
| 带时间词的查询 | ❌ | ❌ | 时间敏感，缓存即过期 |
| 写操作 / 工具副作用 | ❌ | ❌ | 绝不缓存 |

这张表本身就是一个能在面试里讲清楚"为什么不是所有东西都缓存"的点。

---

## 4. 失效策略

- 用户新增/修改记忆 → 失效该 user 的记录类问答缓存（按 user_id 前缀清除）
- TTL 兜底
- 手动失效 API（调试用）

---

## 5. 与 M1/M3 联动

- 缓存命中在 trace 里标记为一个 `cache_hit` span（0 token、~0 延迟）
- M3 统计"缓存节省的 token / 成本" = 命中次数 × 该类请求平均 token × 单价
- 输出一个"缓存命中率 & 成本节省"报告

---

## 6. 验证方式

1. 单测：同一请求两次 → 第二次 L1 命中，不打 LLM
2. 单测：语义相近的两个 query → L2 命中
3. 单测：跨 user 不命中（隔离正确）
4. 单测：带"今天"的 query 跳过缓存
5. 单测：用户改记忆后，记录类缓存失效
6. 集成：跑一批重复+相似 query，统计命中率，对比接缓存前后的总 token
